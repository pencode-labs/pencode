# `make run` 后打开 Onix 的内存分析

2026-11-01，Windows amd64、Go 1.27.3、NVIDIA GeForce RTX 3060。实测项目为 `E:\workspace\onix`，仅打开目录，没有打开源码文件、终端或语言服务器。

普通 `make run` 实例的 GUI 私有驻留约 **107–111 MiB**，服务端约 **31–39 MiB**。最后一次完整进程树采样合计 **155.71 MiB 私有驻留**，包括 GUI、服务端、三个扩展和四个控制台宿主。最大的明确可优化项是服务端逐目录监听：**194 个目录 × 64 KiB = 12.125 MiB** 的常驻事件缓冲。

## 测量方法与边界

- 执行原始 `make run`，完成服务端和扩展安装，观察启动器，再打开 Onix。普通实例 PID 为 GUI `35144`、服务端 `25312`。
- 外部使用 `GetProcessMemoryInfo`、`QueryWorkingSet`、`VirtualQueryEx`、`GetMappedFileNameW` 采样。私有驻留指工作集中不可共享的页面；提交量包含当前未驻留的私有页。两者不能混用；多个进程的总工作集不能直接相加当作独占 RAM。
- 工作集枚举与进程计数器分时取样，通常相差约 0.04 MiB。所有表格使用 MiB（1,048,576 字节）。
- Go 对象归因使用独立 overlay 诊断构建，采样间隔 64 KiB，GUI PID `24112`、服务端 `31836`。没有向生产启动路径加入诊断服务器或采样代码。
- 诊断实例通过主线程读取工作区状态，确认 `E:\workspace\onix`、2153 个条目、0 个打开文件、扫描已完成。保留两个视图（启动器和工作区）。
- Pencode 起始提交 `00041b42a2d6e48543e1adf9372d79e44f0eb227`，Onix 起始提交 `2ea1f1aa746758277603e7b43e7004ead6f9a680`；两者均含原有未提交修改。采样期间 Onix 另有并行开发修改和文件事件，因此这不是完全静止目录的长期泄漏测试。
- 普通实例与稍后生成的诊断实例不是严格冻结源码的 A/B 对照。诊断实例 GUI 私有驻留约 125–128 MiB，高于普通实例；不能把差额全部归因于 profiling，也不能用它宣称优化收益。下文 Windows 总量以普通实例为准，Go 分配来源以诊断实例为准。

## 服务端的主要成本：逐目录监听

GC 后服务端 Go 存活对象约 **18.2 MiB**；采样合计约 17.13 MiB。

| 分配来源 | 采样存活量 | 含义 |
| --- | ---: | --- |
| `fsnotify.(*readDirChangesW).addWatch` | **12.26** | 占采样存活堆约 71.6%，主要是每目录事件缓冲 |
| `server.newServiceStream` | 2.08 | 进程通信、日志流预分配的数据块 |
| `io.ReadAll` | 0.51 | 资源／协议读取 |
| `protocol.(*Encoder).Bytes` | 0.40 | 响应编码缓冲 |
| `serviceIndex.scan` | 0.32 flat / 0.38 cum | 全项目目录索引 |
| 扩展贡献解码 | 约 0.56 | 字符串和贡献记录 |

`server/watch.go` 递归遍历目录，对每个目录调用 `w.watcher.Add(name)`。fsnotify v1.9.0 的 Windows 后端默认缓冲为 **65536 字节**，在 `addWatch` 中通过 `make([]byte, bufsize)` 为每个 watch 分配并长期持有。本次生产目录集合为 **194 个目录**，对应 **12.125 MiB** 纯缓冲容量，与堆采样吻合。这部分是有效引用，强制 GC 不会释放。

隔离实验先调用生产 `workspaceWatch.setup` 取得目录集合，再在独立测试进程里为同一集合注册监听，分别设置缓冲尺寸。每种设置运行一次，GC 后测量净存活堆；没有修改生产配置，也没有进行事件吞吐正确性测试。

| 每目录缓冲 | 194 个目录的缓冲容量 | 实测监听净存活堆 | 相对默认净堆减少 |
| --- | ---: | ---: | ---: |
| 64 KiB（默认） | 12.125 | 12.170 | — |
| 16 KiB | 3.031 | 3.086 | **9.084** |
| 4 KiB | 0.758 | 0.808 | **11.362** |

16 KiB 值值得先验证。较小缓冲更容易在批量检出、生成文件和重命名时溢出；上线前应覆盖溢出后的目录重建、文件树与 Git 状态刷新、删除和重命名、网络路径等。上表是监听器存活堆收益，尚不是 GUI＋服务端的进程驻留降幅。

`server/stream.go` 还有较小的固定成本：每条流在创建时预分配 `StreamWindow / ChunkSize = 8` 个数据块。可以评估小容量启动并按需扩展、热路径复用；不要为了减少空闲容量而让每次读写都重新分配。

两次 GC 快照间隔约 207 秒：

| 进程 | 18:57:40 存活堆 | 19:01:07 存活堆 | 增量 |
| --- | ---: | ---: | ---: |
| GUI | 18.52 | 18.54 | 约 0.02 |
| 服务端 | 18.17 | 18.20 | 约 0.03 |

函数级采样存活分布没有变化。这个窗口内没有持续增长的存活堆证据，但不足以排除长期泄漏或打开／关闭大量文件后的保留问题；诊断采样自身也会制造临时分配。

诊断实例执行一次 `debug.FreeOSMemory()` 后，Go 的未归还闲置堆页降为零，`Sys - HeapReleased` 为 GUI 31.62 MiB、服务端 29.51 MiB；存活对象仍约 18.5／18.2 MiB。外部私有驻留分别从 128.37／36.27 降至 124.73／33.98 MiB。这个对照说明强制归还闲页只影响部分高水位保留，不会消除文件监听、界面对象和原生图形开销，不建议把频繁强制 GC 作为产品方案。

## 优先处理顺序

1. **文件监听缓冲**：先验证 16 KiB 配置；隔离实验已确认约 9.08 MiB Go 存活堆潜力，额外事件处理正确性仍待验证。也可评估 Windows 原生递归监听的设计，但不能直接假设当前 fsnotify 公共 API 已支持完整替换。
2. **CSS／布局状态复用与紧凑表示**：GUI 中该组约 8.62 MiB，是比项目文件条目更大的对象来源。已有计算样式驻留去重，需测新增收益，不能假设这 8.62 MiB 全可省。
3. **进程流预留与客户端接收缓冲**：当前分别约 2.08／0.83 MiB 采样存活量，适合保留小热缓存并限制高水位。
4. 若目标是 GUI 大幅低于 100 MiB，应另做相同场景的原生渲染后端／窗口呈现对照。本次没有测量更换后端收益，也没有将 GPU 显存计为 CPU 驻留内存。

## 第二轮已实施：进程通信流按需分配

修改位于 `server/stream.go`。原来每条进程标准输出／日志流在创建时分配八个 `serviceChunk`，即使没有任何输出也保留整个窗口。现在首次读取仅分配一个块，只有出现积压且无可复用块时才继续分配，最多八块；消费后返回已有空闲队列，后续继续复用。

32 KiB 的有效数据加上每块元数据后，Windows amd64 上单个 Go 分配对象约占 40 KiB。按需分配因此能明显减少多个空闲扩展流的固定开销。首次积压增长允许分配；没有增加空闲计时器、每次读取后的收缩或强制 GC。曾经达到完整窗口的活动流会继续保留这些块以供复用。

使用修改前 `stream.go` 的 overlay 与修改后代码对照，每个版本启动三个独立测试进程，每进程创建 16 条无输出的管道流，等待全部进入阻塞读取，再做两次 GC 并读取净存活堆：

| 版本 | 三轮净存活堆（MiB） | 均值 |
| --- | --- | ---: |
| 修改前 | 5.054 / 5.049 / 5.053 | 约 5.052 |
| 修改后 | 0.674 / 0.679 / 0.674 | 约 0.676 |
| 减少 | — | **约 4.38 MiB，86.6%** |

这是 16 条空闲通信流的隔离测量，不能当成 Onix 完整进程树已实测减少 4.38 MiB。此前 Onix 场景的实际流数、输出积压和内核内存都会影响实际进程收益。

行为及性能验证：

- 256 KiB 窗口仍能按需填满，继续对超出窗口的写入施加背压；连续读取验证输出顺序、完整字节数及 EOF。
- 无输出时与窗口填满时，取消均能释放阻塞读取和写入。
- 既有单字节交互响应、最终字节伴随 EOF、热身后读取零分配测试通过。
- 交互读取对照基准约 2.26／2.14 µs，均为 0 B/op、0 allocs/op；单次短基准只表明没有明显退化，不能宣称稳定加速。最后一轮新实现交互读取为 2.28 µs、32 KiB 读取为 4.96 µs，两者同为零分配。
- 服务端和客户端两包的完整测试通过：`go test -p 1 ./server ./client`。
- 通信流、进程、终端及取消相关定向竞态检查通过；应用构建 `dist/memory-onix-20261101/pencode-optimized-round2.exe` 成功。

本轮同时检查了客户端接收路径：`protocol.Reader` 的单帧复用缓冲上限为 64 KiB；额外的 8 MiB 分片响应释放实验在调用方丢弃结果并 GC 后仅保留约 78 KiB，没有复现大响应被空闲读取循环持续持有。因此没有加入客户端缓冲收缩策略。

诊断对照文件为同一目录的 `stream-before.go.txt`、`stream-measure_test.go.txt`、`stream-{old,new}-overlay.json`、`stream-{old,new}-{1,2,3}.log` 与 `stream-{old,new}-bench.log`。生产回归与内存预算保存在 `server/stream_memory_test.go`。本轮没有重测 GUI 整体驻留，也未进行长时间吞吐压测。
